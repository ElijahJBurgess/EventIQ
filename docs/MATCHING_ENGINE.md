# Matching Engine

How OOO Intelligence calculates match scores between attendees.

---

## Overview

The matching engine is a deterministic, weighted scoring algorithm. It runs as a Deno Edge Function (`supabase/functions/match-engine/`) deployed on Supabase.

**Why deterministic (not AI)?** AI-generated scores are non-deterministic, expensive per match, and opaque to debug. A rule-based scorer can be unit tested, tuned by adjusting weights, audited, and run at scale for thousands of pairs without API cost.

OpenAI is used downstream for explanation and Q&A (Concierge, admin insights) — not for scoring.

---

## Trigger

The engine is triggered in two ways:

1. **Automatically on profile completion** — when a user finishes onboarding and joins an event, the edge function runs for that user against all other attendees at that event
2. **Manually by the owner** — via the `admin-run-matching` utility (not deployed; single-use operator tool)

---

## Scoring Model — V2 (Directional Rubric)

Scores are **directional**: the engine calculates both an `aToB` score (how well Person A meets Person B's needs) and a `bToA` score (how well Person B meets Person A's needs). The composite score displayed to users is derived from both directions.

### Score Components

| Component | Weight | What it measures |
|---|---|---|
| `goalToValueFit` | 35% | Does A's offering align with B's primary goal? |
| `targetPersonFit` | 20% | Is A the type of person B says they want to meet? |
| `needToOfferFit` | 15% | Do A's offers match B's stated needs (exact + near match)? |
| `expertiseFit` | 10% | Do they share relevant areas of expertise? |
| `opportunityCompatibility` | 10% | Are their roles complementary (e.g., Founder + Investor)? |
| `timingConnectionFit` | 5% | Timing and context signals |
| `contextFit` | 5% | Shared interests, communities, industry |

### Reciprocity Labels

Based on the `aToB` vs `bToA` balance:
- **Mutual Benefit** — both directions score well
- **You Can Help Them** — your `bToA` score is high (you can help them more than they help you)
- **They Can Help You** — your `aToB` score is high (they can help you more than you help them)

---

## Needs/Offers Near-Match

The `needs_offers_compatibility` table defines approved near-match pairs. Example:

| Need | Offer | Weight |
|---|---|---|
| Finding Customers | Sales Expertise | 0.7 |
| Raising Capital | Investment Capital | 0.7 |
| Hiring Talent | Talent Referrals | 0.7 |

Exact matches (same string, case-insensitive) are handled directly by the scorer and score 1.0. Near matches use the weight from the table (0.7). Strings not in the table score 0.

---

## Canonical Pair Ordering

Match rows are stored with `user_a_id < user_b_id` (always the smaller UUID). This is enforced by a CHECK constraint. The upsert key is `(event_id, user_a_id, user_b_id)`, so concurrent engine runs for the same pair produce one row, not two.

When reading a match, the app determines which user is "A" and which is "B" and swaps the directional fields accordingly when rendering from the B perspective.

---

## Output

For each matched pair, the engine writes to `matches`:

- `match_score` — composite 0–100
- `match_reason` — human-readable prose explanation
- `score_breakdown` — JSON with per-component scores and `aToB`/`bToA` directional halves
- `match_evidence` — structured evidence for each component
- `match_details` — structured matched pairs (goals, roles, interests, needs/offers) for Full Profile View
- `reciprocity_label` — Mutual Benefit / You Can Help Them / They Can Help You

## Score Distribution Notes

Early testing (40 seed profiles) produced scores clustering too high (most above 80). Root cause: seed profiles had no interests, communities, or conferences filled in, so the context/diversity components had no variance. After backfilling richer seed data, scores distributed more naturally across the full range.

The engine correctly skips:
- Self-matches (A vs A)
- Duplicate pairs (canonical ordering enforces this)
- Pairs where one or both profiles are incomplete

## Known Gaps

- **OpenAI match explanations** — the `ai_explanation` column exists on `matches` but nothing currently writes to it. Match reasons are generated by the rule-based template layer, not AI.
- **Conversation starters** — the `conversation_starters` column exists but is not populated.
- **The "live comparison" Concierge path** — the Concierge function contains code to score a named attendee you haven't matched with yet, but this path is dormant in the current platform-wide Concierge flow (it requires an event roster, which the platform-wide request doesn't carry).
